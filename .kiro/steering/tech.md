# 技術スタック

## アーキテクチャ方針

- **クライアント完結（MVP）**: 将棋ロジック・永続化・検索はオンデバイス。オンライン連携は将来フェーズ。
- **宣言的 UI + 単方向データフロー**: SwiftUI を主とし、View と状態を分離する（MVVM 系の責務分離を基本とする）。
- **ドメインと UI の分離**: 手の合法性・局面表現は将棋エンジン／ドメイン層に集約し、View は表現と操作に専念する。

## 中核技術（確定度の高いもの）

- **言語**: Swift（Xcode 推奨バージョンはプロジェクト設定に追随）。
- **UI**: SwiftUI。
- **将棋ロジック**: SwiftShogi（手生成・局面管理・検証の単一の参照実装として扱う）。
- **永続化**: SwiftData（ローカル）。CloudKit 連携は仕様上「SwiftData + CloudKit」として iOS 17 以降の文脈で扱うが、MVP ではオフライン優先で設計する。

## 開発上の標準

### 型と安全性

- オプショナル・エラーは握りつぶさず、UI またはログに到達可能な経路を決める。
- 将棋の座標・駒・手などは、可能な限り SwiftShogi／ドメイン型で表現し、生のタプルや魔法数字を散らさない。

### 品質

- 手の合法性・検索結果の一貫性はユニットテストしやすい層に置く（UI はスナップショットや結合に依存しすぎない）。
- アクセシビリティ（VoiceOver、十分なタップ領域）は盤 UI の受入条件として扱う。

### テスト

- ドメイン・検索・シリアライズを優先して自動テストする。UI は重要フローのみ手動または少数の自動化に留める。

## 開発環境

### 前提ツール

- Xcode 15 以上（iOS 17 SDK 以上をターゲットにする。最小 OS は `docs/functional-requirements.md` の要件に合わせる）。
- Swift Package Manager でサードパーティを管理する（CocoaPods は採用しない方針）。

## 主要な技術判断

| 判断 | 理由 |
|------|------|
| SwiftShogi を盤面の真実の源泉にする | 手合法判定・局面表現の重複実装を避け、バグの温床を減らす。 |
| SwiftData を第一の永続化にする | 要件・機能仕様で明示。将来のクラウド同期の足がかりにしつつ、まずはローカル完結。 |
| MVP はオフライン機能にフォーカス | ネットワーク・認証・共有の複雑さを後ろに回し、棋譜・検索の体験を先に固める。 |

---
依存ライブラリを増やす場合は「将棋ルールの二重実装を生まないか」「オフライン動作を壊さないか」を必ず確認する。
